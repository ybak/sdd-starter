# OpenSpec 工件模板

本目录提供可复制的工件骨架，而不是一份真实变更。创建新变更时复制四个文件，并按项目 schema 放入对应位置：

```text
openspec/changes/<change-id>/
├── proposal.md                 # 来自 proposal.md
├── design.md                   # 来自 design.md
├── tasks.md                    # 来自 tasks.md
└── specs/<capability>/spec.md  # 来自 spec.md
```

使用规则：

1. 所有 `<placeholder>` 必须替换为事实、明确的 N/A 边界或已知未决项；禁止原样提交。
2. design 的 B0–B3 分档由最高风险决定；B2/B3 不能删除契约、数据、生命周期、身份、迁移、回滚与运维章节，只能填写事实性 N/A。design 的测试策略还必须记录新增 V2/V3/V4 的准入、预计成本、预算影响和 e2e 选择规则。
3. tasks 中 RED 和 GREEN 必须成对出现，且 RED 任务先于对应实现任务；新增慢用例、预算文件和覆盖映射的更新也必须有独立任务。
4. spec 描述可观察行为，不依赖内部类名、临时文件或实现步骤。
5. 提案归档前，将已批准的 delta spec 同步到能力主规格，并保留验证证据。

## Mermaid / UML 按需使用

只有当图能帮助人工理解文字或表格难以清楚表达的关系、交互或状态变化时，才生成 Mermaid 图。简单变更可以不画图，不要求每份工件或每个章节都有图。复制模板后，删除不适用的图块；必要章节仍需保留事实性 N/A 边界。

| 阅读难点 / 生成条件 | 推荐图型 | 放置位置 |
|---|---|---|
| 参与者与用例、业务价值或目标状态难以说清 | 用 `flowchart` 表达参与者与用例关系（兼容 Mermaid 11.x 及常见预览环境） | Proposal 的“期望结果” |
| 系统边界、跨模块依赖或现状到目标的变化难以看清 | `flowchart` 结构 / 流程图 | Proposal 的 Scope 或 Design 第 4 节 |
| 跨服务调用、授权、异步或失败处理的顺序影响契约 | UML 时序图 `sequenceDiagram` | Design 第 6 节 |
| 多个领域对象的职责、继承、组合或多重性需要解释 | UML 类图 `classDiagram` | Design 第 7 节 |
| 持久化实体的外键、归属或基数需要解释 | `erDiagram` | Design 第 7 节；避免与类图重复 |
| 多状态及其转换条件、失败、取消或重试影响行为 | UML 状态图 `stateDiagram-v2` | Design 第 8 节；Spec 仅补充复杂的外部可观察状态 |

- 时序图、类图和状态图属于 UML；`flowchart` 和 `erDiagram` 是辅助结构 / 数据图。为兼容 Mermaid 11.x 及常见预览环境，参与者与用例关系统一使用 `flowchart` 表达，并将角色放在系统边界之外、用例放在边界之内。不要提交 `usecaseDiagram` 代码块。
- 按阅读问题选图，不为凑齐图型增加文档。
- 图前说明要回答的问题及适用场景，明确 AS-IS / TO-BE。只保留关键对象和分支，大图按职责拆分。
- 名称、消息、关系、状态、条件及失败路径必须与实际契约一致；示例不是已确认的设计决策。
- 图不能替代设计论证、契约表格、SHALL 要求、验收场景或验证证据。跨工件优先引用已有图，避免复制后失步。
- 提交前在支持 Mermaid 的 Markdown 预览中检查语法、文字可读性、箭头和分支含义；语法通过不代表业务语义正确。

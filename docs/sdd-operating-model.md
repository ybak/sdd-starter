# SDD 运行模型模板

SDD 的目标不是增加文档，而是让“为什么改、改什么、如何证明、如何安全发布”在同一条证据链上可追溯。

## 1. 工件职责

| 工件 | 回答的问题 | 不应承担的内容 |
|---|---|---|
| Proposal | 为什么现在要改？范围、非目标、影响和验收是什么？ | 逐文件实现清单、完整技术细节 |
| Design | 现状到目标如何变化？选择了什么、放弃什么、风险如何处理？ | 已完成任务的流水账 |
| Spec | 对使用者或相邻系统，什么行为必须成立？ | 具体类名、内部临时实现 |
| Tasks | 以何种顺序把设计变成可验证交付物？ | 模糊的“完成开发”“补测试” |
| Verification record | 实际跑了什么、得到了什么、什么未验证？ | 将失败或跳过包装为通过 |

## 2. 门禁模型

```text
需求 → 变更分流 → Proposal → Design + Specs → Review/Approval
     → RED task → GREEN task → 分层验证 → 文档/契约同步 → Archive
```

- 需要 SDD 的变更没有设计和任务时，不开始实现。
- 改变 API、状态、权限、删除/过期、重试/补偿或部署的未决问题，阻塞相关任务。
- 实施中若发现设计假设不成立，更新 design 并复核；不能在代码中静默改变范围。
- 归档只在规格同步、验证完成和风险处置明确后发生。

## 3. 设计的最小证据链

每个重要决策都应能追到：

1. **事实**：现状、约束、用户需求或可复核数据；
2. **决策**：选择什么、拒绝什么、适用边界；
3. **任务**：哪些 RED/GREEN、迁移、文档和验证工作实现该决策；
4. **证据**：自动化结果、运行证据、审查记录或明确限制。

缺少任一环时，读者无法判断该结论是设计、愿望还是已验证事实。

## 4. 变更分流问卷

在创建 change 前依次回答：

1. 是否改变用户可见能力或对外契约？
2. 是否跨模块、服务、团队、进程或信任边界？
3. 是否读写状态、改变数据归属或数据保留？
4. 是否触及身份、授权、租户、机密、审计或高权限操作？
5. 是否引入异步、外部依赖、重试、取消、删除、过期或补偿？
6. 是否改变构建、发布、配置、监控、告警、容量或回滚？

任一项为“是”或“不确定”时，建立 SDD 变更；全为“否”时，可记录理由后走轻量流程。

## 5. 审查角色

| 角色 | 应核对的重点 |
|---|---|
| 需求/产品 | 问题、目标、非目标和用户验收是否清晰 |
| 架构/后端 | 影响评估、契约、数据归属、生命周期、权限和回滚 |
| 测试 | 测试金字塔放置、RED/GREEN、隔离、e2e 必要性和预算 |
| 运维/安全 | 配置、机密、观测、发布、权限、故障与删除风险 |
| 实施者 | 任务可执行性、证据完整性、文档同步和限制披露 |

同一人可以兼任多个角色，但审查维度不应被省略。

# 测试用例增长与回归耗时治理

测试套件必须随风险增长，而不是随代码行数、目录数或“每次改动都加一条 e2e”的习惯线性膨胀。本规范约束**新增什么、放在哪层、花多少时间、超限如何处理、何时跑全量**。

## 1. 不可协商规则

1. **先证明缺口，再新增用例**：新增测试前写明它防止的具体回归；“提高覆盖率”不是充分理由。
2. **断言放在最低有效层**：能由 V1/V2/V3 证明的断言不得仅放在 V4。
3. **一条 e2e 只验证不可替代的真实事实**：浏览器、真实登录、部署入口或外部边界；不把纯规则、路由细节、列表排序或错误映射堆入 e2e。
4. **一个行为一个主断言位置**：允许高层做少量端到端抽样，但同一细节不能在所有层复制成多份慢测试。
5. **超预算是缺陷**：不得靠增加重试、放宽断言、延长 timeout、增加机器或提高并发来掩盖；先重分配覆盖。
6. **未知映射按更大范围运行**：覆盖映射缺失、失效或无法解释时，执行全量受影响套件，而不是少跑。
7. **用例数减少同样需要解释**：删除、跳过、过滤和选择结果都必须可审计，防止“变快”掩盖验收缺口。

## 2. 新增用例准入记录

每个新增 V2/V3/V4 用例，在 proposal、design 或 tasks 中至少记录一行：

| 字段 | 必填内容 |
|---|---|
| 行为 / 风险 | 要阻止的具体错误及影响 |
| 首选层 | 为什么该层能覆盖 |
| 更低层评估 | V1/V2/V3 中哪些层不足，事实是什么 |
| 重复覆盖 | 已有测试是否覆盖相同行为；若是，为什么不能扩展已有测试 |
| 预计成本 | 首次运行、常规运行、外部依赖或串行限制 |
| 资源与清理 | V3/V4 使用的账号、数据、命名和清理方式 |
| 维护归属 | 覆盖映射、预算与失败排障的维护者或团队 |

V4 还必须说明：为什么 V2/V3 无法证明该用户可见或跨边界事实。写不出理由时，默认拒绝进入 V4。

## 3. 用例组合的设计边界

| 目标 | 首选做法 | 禁止做法 |
|---|---|---|
| 覆盖输入组合 | 参数化 V1 测试、性质测试或表驱动测试 | 为每个输入组合启动一套服务或浏览器 |
| 覆盖 API/路由 | V2 契约/装配测试 | 每条 API 都通过页面 e2e 覆盖 |
| 覆盖错误映射 | V1/V2 使用真实 client 与协议替身 | 用 e2e 等待错误提示作为唯一证明 |
| 覆盖发布装配 | V3 少量正向冒烟 | 为每个配置排列组合跑完整 e2e |
| 覆盖真实用户路径 | 每条关键旅程一个 V4 spec | 每个页面、按钮或后端分支各建一个 V4 spec |
| 覆盖历史缺陷 | 在最早能复现的层固定回归 | 永久把偶发环境失败保留在高层 |

测试名称以行为和结果命名，不以实现文件或缺陷编号命名。一个测试文件可有多个场景，但同一场景不应跨层无理由复制。

## 4. 预算与历史基线

采用项目必须把预算放到一份版本化、机器可读的单一文件中，推荐从 `verification-budget.example.yaml` 复制。该文件定义：

- 每层的预算秒数；
- 本机 `warn`、CI/发布 `enforce` 的判定模式；
- 历史窗口、相对劣化阈值与最小绝对增量；
- 预算为空时的显式含义；
- e2e 子集与全量是否共用预算；
- 用例数、断言数和跳过数的基线来源。

每次统一验证至少记录：层名、耗时、提交标识、运行模式、选中的 e2e spec、执行/跳过数量。历史不足时只能说明“尚无基线”，不能关闭预算。

## 5. 超预算处置顺序

发现超限或显著劣化后，按顺序处理并记录结论：

1. **去重**：删除或合并重复验证同一事实的测试；保留最低有效层的主断言。
2. **下移**：把可以由 V1/V2/V3 覆盖的 V4 断言先在目标层补 RED/GREEN，再从 V4 删除。
3. **消除固定开销**：复用只读准备、缩小无价值轮询、按需要启动依赖；不得把共享可变状态引入并行用例。
4. **隔离资源争用**：用唯一前缀、清理与结构性串行限制解决竞争；并发只在资源确实隔离后增加。
5. **修复依赖问题**：把不可控外部调用移到专项验收或替身集成层；不要将其重试成绿色。
6. **最后才调整预算**：只有全部断言不可下移且成本被明确接受时，修改预算、记录理由、审查人和复核日期。

禁止的“修复”：增加 retry、吞掉失败、全局延长 timeout、提高 CI 机器规格、无限制增加 worker、删除断言或扩大跳过名单。

## 6. 按改动选择 e2e

日常合并请求可以运行受影响 V4 子集，发布和定期回归必须运行全量。采用项目维护一份版本化覆盖映射，推荐从 `e2e-coverage-map.example.json` 复制。

映射至少分四类：

| 类别 | 语义 | 运行策略 |
|---|---|---|
| `alwaysFull` | 登录、认证、共享基础设施、测试 fixture、全局配置或其他高扇出路径 | 全量 V4 |
| `specs` | 源码路径到 V4 spec 的显式映射 | 登录前置 + 命中 spec |
| `noE2e` | 已由 V1/V2/V3 覆盖的路径，必须注明覆盖位置 | 不跑 V4，但仍跑对应低层 |
| `nonCode` | 不影响运行行为的文件 | 不跑 V4 |

映射守卫应自动检查：每个 V4 spec 已登记；每条 glob 匹配至少一个现存文件；分类不重叠；`noE2e` 有可追溯的低层覆盖。任何未匹配的可执行代码路径都按 `alwaysFull` 处理并输出警告。

## 7. V4 子集与全量的职责

- **提交前**：运行最小相关 V0/V1/V2，快速发现局部缺陷。
- **合并请求**：运行受影响 V0–V3 与由覆盖映射选择的 V4；输出选择理由和未选 spec 数。
- **发布 / 定期回归**：使用 `enforce` 模式执行所有层与全量 V4；这是唯一可声明为完整回归的结果。
- **专项真实环境验收**：与常规 V2 分开标识，明确真实依赖、凭据来源、负责人和失败语义。

“本次无受影响 e2e”必须输出映射依据；不能只因命令运行很快而视为通过。

## 8. 断言数量、跳过和不稳定性

- V3/V4 每次输出执行、失败、跳过及条件跳过原因；数量下降默认需要调查。
- 只允许对明确的不适用前置做条件跳过；缺少验收环境时应失败或标为未运行，不允许把验收用例自动 skip。
- 原样重跑转绿必须进入不稳定性登记；同一根因达到团队阈值后，修复、隔离或下移断言。
- 覆盖率阈值只能作为辅助指标；不得用增加低价值测试提高数字来替代行为、契约或运行证据。

## 9. 评审检查表

- [ ] 新增用例有行为/风险、最低层和成本说明。
- [ ] 新增 V4 已说明低层无法覆盖的不可替代事实。
- [ ] 预算文件和历史记录覆盖新增层或新增 spec。
- [ ] 映射变更已通过守卫；未知路径采取全量安全缺省。
- [ ] 超预算处置没有使用重试、放宽、超时或机器扩容替代覆盖重分配。
- [ ] MR 子集结果与发布全量结果被清楚区分。

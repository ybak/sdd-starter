# 验证策略模板

本文件定义验证体系的目标和裁决规则。实际命令、时限、测试环境和负责角色由采用项目补充；它们应有唯一事实来源，避免在多个文档中复制后漂移。

## 1. 分层与职责

| 层 | 覆盖对象 | 应当具备的性质 | 不应承担的职责 |
|---|---|---|---|
| V0 静态 | 格式、类型、依赖规则、机密扫描 | 快、确定、无需服务 | 真实运行期装配 |
| V1 单元 | 纯逻辑、边界、失败处理 | 快、隔离、可并行 | 多模块 wiring 或浏览器行为 |
| V2 集成 | 真实组装、路由、模块契约 | 自给自足，不读真实凭据、不连真实外部服务 | 云资源、共享环境和完整用户旅程 |
| V3 构建/冒烟 | 可发布产物、配置装配、关键服务连通性 | 使用接近部署的进程或容器 | 覆盖所有界面细节 |
| V4 e2e | 用户路径、浏览器、真实跨边界行为 | 使用真实入口和受控账户/资源 | 代替所有低层测试 |

原则是：**越靠后的层越少、越关键、越难替代**。如果一个 V4 用例只验证纯转换逻辑或单一路由，应将该断言下移到 V1/V2/V3。

## 2. 可观察的正向证据

以下任一证据可以支持“功能生效”，但必须与变更目标直接相关：

- 目标 API 或事件返回预期的状态、主体和副作用；
- 服务日志或指标显示预期组件已注册、已处理或已完成；
- 浏览器中关键用户可见元素出现，且请求实际抵达正确入口；
- 数据状态、审计记录或产物符合设计中的归属和生命周期约束；
- 对应的自动化断言通过，且前置环境没有被跳过。

仅有进程健康、构建通过、HTTP 非 500 或命令退出码为零，不足以证明新能力已装配或可用。

## 3. 测试先行

每个行为改动采用：

1. 写出一个明确描述行为和失败条件的测试；
2. 在缺少实现时运行并记录预期 RED；
3. 以最小实现使其 GREEN；
4. 在同一或更高层补足必要的契约、装配或用户路径验证；
5. 如实记录命令、结果、跳过项和限制。

禁止通过放宽断言、增加重试、扩大超时或删除用例来把未知失败伪装为成功。若测试本身不稳定，登记其症状、频率、影响、临时处置、负责人和修复截止点。

## 4. 真实环境与 e2e

真实环境用例有成本，也有不可替代性。采用项目必须定义：

- 环境和账户的创建、权限、轮换和清理方式；
- 每个用例资源的唯一命名和清理机制；
- 哪些情形是硬失败，哪些前置尚未提供；
- 哪些真实依赖允许偶发故障，以及如何登记而不是重试掩盖；
- 浏览器测试应指向构建后的真实入口，而非仅开发服务器。

共享环境中，断言应只观察本用例创建的资源，不能依赖列表长度、第一条记录或“环境为空”。覆盖映射未知时默认扩大 e2e 范围。

## 5. 时间预算与测试增长治理

为每层定义预算并长期记录耗时。预算超限的优先处置顺序是：

1. 把可下移的断言移到较低层；
2. 去除重复的环境准备和无价值等待；
3. 修复串行瓶颈、资源争用或不稳定依赖；
4. 仅在断言确实无法下移时，带理由调整预算。

不要用“增加机器、增加并发、增加重试”替代以上分析。明显变快与明显变慢都需要调查：前者可能意味着断言被删除或跳过，后者可能意味着回归退化。新增 V2/V3/V4 用例必须先说明风险、低层不足、预计成本和预算影响；MR 的 V4 子集选择与发布全量回归必须明确区分，未知映射按全量处理。

完整的准入表、预算样例、覆盖映射和超预算禁止性规则见 `test-growth-governance.md`。

## 6. 结果记录格式

建议每次交付在变更的 `tasks.md` 或合并请求中保留：

| 检查 | 范围 | 结果 | 正向证据 / 限制 |
|---|---|---|---|
| V0 | `<affected paths>` | 通过/失败/未运行 | `<command or reason>` |
| V1/V2 | `<modules>` | 通过/失败/未运行 | `<counts or key assertion>` |
| V3 | `<runtime>` | 通过/失败/未运行 | `<health plus feature evidence>` |
| V4 | `<user paths>` | 通过/失败/未运行 | `<browser or external boundary evidence>` |

“未运行”必须写出原因和下一步，不能写成“通过”。
